# Known-unwired CLI flags — the backlog of issue #1089.
#
# Every line here is a flag that clap accepts, `azlin --help` advertises, and
# no handler ever reads. The user gets no error; the command simply does
# something other than what they asked for. This file exists so that the
# check in `crates/xtask` can ship GREEN against the existing backlog and
# still block the NEXT occurrence on the day it is written. It is a debt
# ledger, not a permission list.
#
# Format (the reason is mandatory):
#
#     Enum::Variant::field = why this is temporarily tolerated
#
# Rules:
#   - Shrinking this file is the point. Fixing a flag means deleting its line;
#     the check FAILS on a stale entry, so the ledger cannot drift.
#   - Adding a line is a review-visible admission that a flag lies to the user.
#     Prefer wiring the flag, deleting it, or hiding it from `--help`.
#   - The reason quotes the flag's own `--help` text, so the gap between what
#     azlin promises and what it does is readable straight from this file.
#
# Generated from the checker's report against commit fdfb27a2 (v2.6.105).

# ── What is left, and why (11) ───────────────────────────────────────
#
# The straightforward backlog is gone: every flag that could be fixed by binding
# a field in a handler and acting on it has been. What remains is here on
# purpose, and each entry says which of three things it is:
#
#   - a flag naming a feature that does not exist, where "wiring" it means
#     building the feature (seven of these)
#   - a flag whose absence hides a real bug, filed separately (one)
#   - a documented no-op kept for compatibility, which does not lie to anyone

Commands::Ask::max_results = #1089 — `azlin ask --max-results` accepted, then discarded.
#   Like `top --interval` below, this one names a thing the command does not have. `azlin ask`
#   sends one question to the model and prints the one answer that comes back; there is no
#   result list to cap, and nothing in the output is countable as a "result".
#
#   It could be wired by asking the model to keep any list in its answer to N items — but a
#   flag whose enforcement is "we asked the model nicely" is the same lie in a politer form,
#   and truncating free-form prose at N "results" has no defensible definition. The other
#   honest option is deleting the flag, which is a breaking CLI change. Both are decisions for
#   the repository owner, so this is recorded rather than guessed at.
Commands::Session::resource_group = #1089 — `azlin session --resource-group` accepted, then discarded.
#   `azlin session` reads and writes `session_names` in the local config and never contacts
#   Azure, so there is nothing for a resource group to scope. It is not a harmless flag,
#   though: the map is keyed by VM name alone, so two VMs called `dev` in different resource
#   groups share one session name today, silently — filed as #1122, so the bug is findable
#   somewhere other than a flag-wiring debt file.
#
#   Wiring the flag properly means scoping sessions per resource group — a config schema
#   change with a migration, and a behaviour change for anyone relying on the current
#   collision. Deleting the flag leaves that bug in place but stops advertising a fix for it.
#   Both are decisions for the repository owner, so this is recorded rather than guessed at.
Commands::Gui::yes = Documented no-op, kept for compatibility. Its help says so in as many
#   words — "Compatibility flag; GUI dependency setup is already non-interactive" — so unlike
#   every other line in this file it is not lying to anyone: a user who reads `--help` learns
#   exactly what passing it will do, which is nothing. It is listed here because the checker
#   asks only whether a field is read, and this one never is.
#
#   Hiding it from `--help` would satisfy the checker and make the flag less discoverable to
#   the scripts that pass it. Deleting it would break them. Neither is an improvement, so it
#   stays as it is, deliberately.
Commands::Top::interval = #1089 — `azlin top --interval` accepted, then discarded. Unlike its
#   sibling `--timeout` (wired), this one cannot be wired without deciding what `azlin top`
#   *is*: it takes one snapshot and exits, so honouring a refresh interval turns it into a
#   loop that never returns — a behaviour change that would hang every script calling it.
#   Either `top` grows a repeating view (as `health --tui` already has) or this flag goes.
#   Left here deliberately rather than wired the wrong way.
Commands::Cleanup::idle_days = #1089 — `azlin cleanup --idle-days` accepted, then discarded.
#   These three describe a feature that does not exist. `azlin cleanup` deletes orphaned
#   *resources* — unattached disks, NICs, public IPs and NSGs — and never touches a VM, so
#   there is no idle VM to threshold, none to include, and no named session to spare. Its
#   sibling `--age-days` was wired in the same pass because it applies to what the command
#   actually deletes.
#
#   Wiring these means building VM deletion by idleness: a new destructive feature with its
#   own design (what counts as idle, measured how, over what window) and its own blast
#   radius. Deleting the flags is the other honest option and is a breaking CLI change.
#   Both are decisions for the repository owner, so they are recorded here rather than
#   guessed at.
Commands::Cleanup::include_running = #1089 — see Commands::Cleanup::idle_days above.
Commands::Cleanup::include_named = #1089 — see Commands::Cleanup::idle_days above.
Commands::Code::no_extensions = #1089 — `azlin code --no-extensions` accepted, then discarded.
#   Like `ask --max-results`, it names something the command does not do. `azlin code` opens a
#   `vscode-remote://` URI and installs nothing; VS Code's own Remote-SSH decides which
#   extensions to install on a host, from the user's settings, and azlin is not in that
#   conversation. There is no install here to skip.
#
#   Wiring it means azlin taking over remote extension management — a feature with its own
#   design and its own way to be wrong. Deleting the flag is the other honest option and is a
#   breaking CLI change. Both are decisions for the repository owner.
GuiAction::Install::yes = Documented no-op, kept for compatibility. See Commands::Gui::yes above.
GithubRunnerAction::Enable::auto_scale = #1089 — `azlin github-runner enable --auto-scale`
#   accepted, then discarded. It names a feature that does not exist. `enable` provisions
#   `--count` VMs once and writes a TOML file; nothing watches a queue, nothing creates or
#   removes a runner afterwards, and there is no process left running to do either.
#
#   Wiring it means building a scaler: something that polls GitHub for queue depth, decides
#   when to add and when to remove, and survives between azlin invocations. That is a service,
#   not a flag. Deleting it is the other honest option and is a breaking CLI change. Both are
#   decisions for the repository owner.
#
#   The same handler provisions VMs with public IPs (#1123) and exits 0 when they fail to
#   provision; neither is fixed by this flag and both outlive it.
CostsAction::Dashboard::refresh = #1089 — `azlin costs dashboard --refresh` accepted, then discarded.
#   It names a cache that does not exist. The dashboard fetches every figure from Azure on
#   every run — `get_cost_summary`, then `az consumption usage list` — and nothing is stored
#   between runs, so there is nothing stale for a refresh to bypass. (azlin's one cache is a
#   process-local VM list with a TTL, which a one-shot CLI can never reuse across runs either;
#   `list --no-cache` has the same shape and is out of scope here.)
#
#   Wiring it means building a cost cache first — a file, a TTL, an invalidation rule, and a
#   decision about stale cost figures being shown at all. Deleting the flag is the other honest
#   option and is a breaking CLI change. Both are decisions for the repository owner.
